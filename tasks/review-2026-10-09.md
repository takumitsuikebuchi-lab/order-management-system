# 本番稼働1年 網羅レビュー 統合レポート（2026-10-09）

対象: order-management-system（本番 1,420件・顧客 239件・簡易マスタ 69件）
方法: サブエージェント3体（コード品質・セキュリティ／テスト・CI・運用継続性／設計・長期保守）＋ 本番データの読み取り点検＋ 外部サービスの現況確認（WebSearch/WebFetch、2026-10-09）。
コード・DBは無変更。🔴🟡の各項目は、サブエージェントの報告を実物（コード行・本番データ・公式ドキュメント）で一次検証済み。

## 総合評価: ⭐⭐⭐☆☆

アプリ本体の日常機能（登録・一覧・印刷・請求書CSV・消費税計算・競合検知・XSS対策）は健全で、1年分のデータにも整合性の問題はない。
一方で **「守り」の側に穴が3つ**（バックアップ欠損・バックアップ自動停止の期限・接続キーの廃止期限）あり、いずれも放置すると「気づかないうちに復旧不能」になる型。これらは小修正で塞げる。
中長期では「全件を端末に持つ」設計の限界（localStorage 上限・通信量）が 2027〜2030 年に順に来る。

## 🔴 Critical（即対応）

### 1. 週次バックアップが 1,000 件で頭打ち。2026-08-10 以降の受注 414 件が一度もバックアップされていない
- `.github/workflows/weekly-backup.yml:53` `page_size=10000`。PostgREST は1回の応答を 1,000 行に制限するため、1ページ目で 1,000 行を受け取った後 offset が 10,000 に飛び、2ページ目を取りに行かない
- 一次検証: 非公開リポの `2026-08-12`〜`2026-10-07_受注明細.csv` は**全部ちょうど 1,000 行・最終日付 2026-08-10**。本番は 1,420 件（`Content-Range: 0-999/1420`）
- ログの「受注明細: 1757 行」は備考欄の改行を数えているだけで検知になっていない
- 実害: 今 Supabase を失うと 8月中旬〜10月の全受注が復元不能
- 修正: `page_size=1000` ＋「CSVの行数 == Content-Range の総数」を検証して不一致なら失敗にする ＋ 修正後に手動実行して 1,420 行を確認

### 2. 公開リポジトリのスケジュール実行は「60日間コミットなし」で自動停止 → 2026-11-03 に週次バックアップが止まる
- GitHub 公式: "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days."（2026-10-09 確認）
- 最終コミット 2026-09-04。これまでは週次バックアップ自身がこのリポへ push していたので活動扱いだったが、9/4 に push 先を非公開リポへ移したため活動が止まった
- 実害: 11月以降、誰も気づかないままバックアップが停止（1と重なると被害拡大）
- 修正: バックアップ workflow を非公開リポ `kyoshin-order-backups` 側へ移す（非公開は60日ルールの対象外。cloud-config.json は公開URLから取得できる）。暫定なら月1回のコミット運用

### 3. Supabase の旧形式キー（anon key）が 2026 年末までに廃止予定。切替にはコード修正が必要
- 公式: "Supabase is deprecating the anon and service_role keys by the end of 2026."（2026-10-09 確認。自動無効化の日付は未記載）
- 新形式 `sb_publishable_…` は `apikey` ヘッダのみで送る仕様。現状は `index.html:1418-1425 supabaseHeaders()` と `weekly-backup.yml` が `Authorization: Bearer` にも載せており、CI の照合 `guard-and-sync.yml:41` は `eyJ` 始まりしか受け付けない。`SETUP.md` も「sb_publishable_ は非対応」と記載
- 修正箇所: `supabaseHeaders()`（キーが eyJ 始まりのときだけ Authorization を付ける）/ CI 正規表現 / weekly-backup.yml / cloud-config.json / index.html 埋め込み / SETUP.md・RUNBOOK.md / setup-wizard.html。年内に新キーを発行して併用期間中に切替

### 4. 同期キューが、通信失敗した「更新」「削除」を黙って捨てる
- `index.html:1540-1571 flushCloudQueue`: `cloudUpdateOrder`(1989) / `cloudDeleteOrderByOrderNo`(2041) / `cloudBatchUpdate` は失敗時に内部で catch してキューへ再投入し、例外を投げずに戻る → `processed++` され、最後に flush 開始時のスナップショットでキューを上書きするため、再投入分も flush 中に追加された分も消える（upsert だけは例外が伝播して残る）
- 実害: Wi-Fi 断や Supabase 障害中に「請求済」をチェック・受注を削除 → 30秒後の flush で消え、表示は「同期完了」。60秒後の同期でチェックが外れ、削除した受注が復活して請求書CSVに載る
- 修正: 成功した item だけを「現在のキュー」から取り除く。flush 経由の呼び出しでは再投入せず例外を投げる。オフライン時は flush をスキップ

### 5. 顧客マスタ・簡易マスタの保存が「全件 DELETE → INSERT」のまま
- `index.html:2171 cloudSaveCustomers`（呼び元 2884 保存ボタン、5025 CSV取込）、`2235 cloudSaveSimpleMaster`（3122、3243＝await なし）
- 2026-04-02 に直したのは「＋新規追加」だけ。DELETE 成功直後に通信が切れて INSERT が失敗すると、クラウドの顧客が 0 件になり、他端末は「空＝正」仕様で 60 秒以内にローカルも空にする
- 修正: id をキーにした upsert ＋ 画面で消した行だけ個別 DELETE。または Postgres 関数で1トランザクション化

### 6. anon key 公開 ＋ RLS 全許可（既知・設計判断が必要）
- `schema.sql:65-86` 3テーブルとも `using(true) with check(true)`。キーと URL は公開リポ・公開ページ上にあるため「URL が知られていない」は守りにならない。レビュー中もキーだけで顧客 239 件（住所・電話）が全件取得できた
- 対策案（工数小→大）: A) 新キーへの移行 ＋ 「1文で2行以上の DELETE を拒否するトリガー」＋ バックアップ日次化（読取は防げないが一括削除事故を限定）/ B) Supabase Auth（担当者のメール＋パスワード）＋ RLS を authenticated 限定（要件「URLを開くだけ」が「URL＋ログイン」に変わる）/ C) BFF（Edge Function 等）に秘密キーを置く

## 🟡 Warning（早めに対応）

### 7. 朝 9 時前に登録すると、日付と受注番号が「前日」になる（実データ 23 件すべてが該当）
- `index.html:2770`（新規モーダルの日付初期値）と `3352`（受注番号採番）が `toISOString()`（UTC）。JST 0〜9時は前日
- 本番検証: JST 9時前に登録された 23 件は全件、受注番号の日付が前日。うち `R260903-018`（9/4 08:55 登録・日付欄 9/3）`R261007-005`（10/8 07:33 登録・日付欄 10/7）は日付欄も前日のまま＝実際の配送日と違う可能性があるので要確認
- 実害: 月初の朝一番の受注が前月扱いになり請求月がずれる
- 修正: ローカル日付を返す関数を utils.js に作り 4 箇所（2770 / 3352 / 2638 / 2681）で統一

### 8. 「請求済」チェックが行全体を上書きし、他端末の直前の修正を消す
- `index.html:1995 cloudUpdateOrder` が `serializeOrderForCloud({...o, ...patch})` で全列 PATCH。`cloudBatchUpdate`(2022) は差分のみで正しい
- 実害: 端末Aが住所を修正した 60 秒以内に端末Bがチェック → Bの古い住所で上書き。要件 §5.6「後勝ちで静かに上書きしない」に反する唯一の経路
- 修正: 1995 行を `serializeOrderForCloud(patch)` に（1行）

### 9. 同じ受注を 60 秒以内に 2 回編集すると「別の端末で更新されています」と誤って止められる
- `index.html:1949-1952` upsert の応答から `id` だけ反映し `updated_at` を反映しないため、2回目の保存で自分の更新を他端末の更新と誤判定（Playwright で再現）
- 通信失敗時は逆にチェックなしで保存する（fail-open）
- 修正: upsert 応答の `updated_at` をローカルに反映。確認できなかったときは confirm で保留

### 10. バックアップ CSV をアプリの「CSV取込」では復元できず、復元手順も存在しない
- 受注: 真偽値が `t`/`f`（PostgREST 出力）だが `index.html:4889` は `true`/`1`/`TRUE` しか真にしない → 請求済等が全件 false で復元される
- 顧客・簡易マスタ: 取込側のヘッダ判定が日本語列名のみ（`4982`、`3194`）。バックアップは `id,customer_name,...` なので顧客名に id が入る
- RUNBOOK/SETUP に「バックアップから Supabase へ戻す手順」なし。SETUP の「CSV出力で全データ」は当月のみ（`4679`）
- 修正: 取込で `t`/`f` を解釈（1行）＋ 復元手順を RUNBOOK に新設（Supabase の Table Editor「Import data from CSV」で列名一致のまま投入）＋ 使い捨てプロジェクトで1回リハーサル

### 11. localStorage の上限で「同期中のまま固定・一覧が空」になる（約 9,000 件 ≒ 2030 年春）
- `index.html:1279 saveData()` は `localStorage.setItem` を try/catch していない。`applyFetchedOrders`(1877) は `saveData()` を `renderTable()` より先に呼ぶ → 容量超過で例外 → 描画・状態更新に到達しない
- Chromium 実測: 9,000 件は成功、9,100 件で「接続: Cloud（同期中）」のまま一覧 0 行。`toggleInvoice`/`deleteOrder` も同じ経路で止まる
- 現在 1.69MB（上限 10MiB の 17%）、3MB 警告トーストは 2027 年 5〜8 月頃から毎起動で出る見込み。文言は「クラウド同期への切替を」で運用実態（常時 Cloud）と矛盾
- 修正: ① `saveData` を try/catch し失敗しても描画を続行（即）② 「月単位取得＋列指定」へ設計変更（2027 年前半まで。下記 12 も同時に解消）

### 12. 60 秒ごとに全件取得しており、通信量が月 1.5GB/タブ。Supabase Free の 5GB 枠に近い（要確認）
- `index.html:1577` 60 秒ごとに `cloudFetchOrders`（全件 `select=*`）。1 回 138KB（gzip）× 8h × 22 日 ≒ 1.46GB/月/タブ。2〜3 タブ常時なら現在でも 3〜4.5GB
- 3 年後（約 7,700 件）は 1 タブで 7.9GB → Free では確実に超過
- 確認事項: Supabase ダッシュボードの Usage で現在の egress を確認。プランが Free か Pro かで対応の緊急度が変わる
- 修正: `updated_at=gt.<前回取得時刻>` の差分取得（`orders.updated_at` とトリガーは既にある）。または 11-② の月単位取得

### 13. クラウドが「正常だが 0 件」を返すとローカルの受注も空で上書きされる
- `index.html:1877-1892 applyFetchedOrders`: `Array.isArray` のみ判定で空配列を正として `saveData()`。SETUP.md の「0 件になったらクラウドを無効化してローカルから CSV 出力」は 60 秒同期で先に消えるため成立しない
- 修正: 「ローカルに N 件あるのにクラウドが 0 件」のときは上書きせず警告して止める（空マスタ仕様とは別扱い）。SETUP の該当節を修正

### 14. 印刷ウィンドウ（引取書・運行指示書）で運転者・車両・単位が未エスケープ
