## 2026-03-13: 全端末ボタン動作不良の調査失敗から学んだこと

### 状況
- 複数端末でボタンが反応しなくなった問題を調査
- Chrome拡張（IBM Rapport, McAfee）を原因と断定し、拡張無効化やコード回避策を何回も試した
- 実際の原因は (1) `?.` / `??` 構文の古いブラウザ非互換 (2) SupabaseのUUID IDがinline onclickを壊していた

### 教訓
1. **環境を疑う前にコードを疑え**: 「端末ごとに違う挙動」→ まず「コード内にデータ/環境依存で壊れる箇所がないか」を調べる
2. **仮説が外れたら即座に捨てろ**: 拡張を無効にしても直らなかった時点で、拡張仮説は棄却すべきだった
3. **修正を重ねる前に原因を特定しろ**: イベントデリゲーション変換、<a>タグ化、アクションバー…と無関係な変更を積み重ねて問題を複雑にした
4. **ブラウザ互換性チェックを早期にやれ**: `?.` `??` `catch {}` などES2020+構文がないかgrepで確認するのは数秒でできた
5. **IDがonclickに埋め込まれるパターンでは型安全性を確認しろ**: 外部DBから来るIDは文字列/UUIDの可能性がある
6. **「なぜ端末Aでは動いて端末Bでは動かないか」を構造的に説明できるまで手を動かすな**

## 2026-03-17: 共有クラウド設定とブランチ運用の事故から学んだこと

### 状況
- 共有クラウド設定の自動読込を別AIが危険変更と誤認し、`cloud-config.json` と関連コードを差し戻した
- その結果、新しいブラウザや新しい端末では共有クラウドに繋がらず、再び端末依存の運用に戻る危険があった
- さらに GitHub のデフォルトブランチが `master` のままで、実運用の `main` とズレていたため、AI ツールが誤った基準を見やすい状態だった

### 教訓
1. **「今動いている根拠」を記録しろ**: 共有クラウド設定や本番 Supabase の正本は、コードだけでなく運用メモにも明記しておく
2. **デフォルトブランチは実運用に合わせろ**: 実際の正本が `main` なら、GitHub の default branch も `main` に揃える
3. **保険を一段入れろ**: `cloud-config.json` が消えても最低限起動できるよう、`index.html` 側にも埋め込みフォールバックを持つ
4. **互換維持ブランチは自動同期させろ**: `master` を残すなら、人手ではなくワークフローで `main` から同期させる
5. **AI に触らせる前提を先に固定しろ**: `AGENTS.md` と `SETUP.md` を先に読ませるだけで、危険な差し戻しをかなり防げる

## 2026-03-18: 一覧フィルタはバックグラウンド同期で壊してはいけない

### 状況
- 顧客検索で受注一覧を絞り込むと、数秒後に全件表示へ戻り、また検索結果に戻る不安定な動きが出た
- 原因はクラウド再読込時の `renderTable()` が、フィルタ状態を復元せずに一覧だけ描き直していたことだった
- あわせて検索UIが「汎用検索」と「顧客検索」に分かれていて、解除手段も分かりにくかった

### 教訓
1. **バックグラウンド同期はUI状態を尊重しろ**: データ更新で再描画するなら、検索条件・選択状態・スクロール位置なども必要に応じて復元する
2. **入力欄が複数あるなら役割を明確にしろ**: 同じ目的の検索欄が2つあると、利用者も保守者も挙動を誤解しやすい
3. **クリア動線は1つに絞れ**: 似た名前のボタンを複数置くより、解除対象が明確な1ボタンの方が事故が少ない
4. **表示不安定でも、まず保存ロジックではなく再描画ロジックを疑え**: 今回はデータ欠損ではなく、同期後の表示復元漏れが本体だった

## 2026-04-02: 顧客マスタの新規登録がリロード後に消える不具合

### 状況
- 顧客マスタで「＋ 新規追加」しても、ページをリロードすると登録した顧客が消える不具合が発生
- 調査の結果、複合的な3つの原因が絡み合っていた

**原因①: 全件DELETEのURLが長すぎてHTTP 400で拒否されていた**
- 元の実装は `customers?id=in.("uuid1","uuid2",...)` の形式でDELETEしていた
- 顧客が1,000件いると URLが39,000文字になり Supabase に拒否された
- DELETEは握りつぶして INSERT だけ実行 → 旧データ+新データで重複が蓄積
- 結果、Supabase の customers テーブルが30,847件まで膨れ上がっていた

**原因②: cloudFetchCustomers が1,000件上限で途中までしか取得しなかった**
- Supabase REST のデフォルト上限は1,000件
- 新しく追加した顧客は末尾に入るため、1,001件目以降は取得されず「消えた」ように見えた

**原因③: 新規追加ごとに全件DELETE+再INSERTをしていた設計が根本的に危険だった**
- 1件追加するだけなのに、全1,000件を削除→再投入していた
- 削除と投入の間（ほんの一瞬）でもリロードされると、Supabaseが空 → 全顧客消失
- 非同期の fire-and-forget で呼んでいたため、保存完了前のリロードでも消失した

### 修正の最終形（Codex）
- `cloudInsertCustomer()` を新設：1件だけをSupabaseへINSERT。成功してからローカルに反映
- `cloudFetchCustomers()` をページング取得へ変更：Rangeヘッダで1,000件ずつ全件取得
- Supabase上の重複838件を削除し163件に正常化

### 教訓
1. **「1件追加」に全件DELETE+再INSERTを使うな**: 削除と挿入の間にリロードされただけでデータが全消滅する
2. **非同期の fire-and-forget は「消えても良いデータ」にしか使うな**: 保存が終わる前にページを離れられたら終わり
3. **Supabase REST にはデフォルト1,000件上限がある**: `limit` を明示しないと切り捨てられる。大量データは必ずページングする
4. **URLにデータを並べるな**: ID一覧を `?id=in.(...)` でURLに展開するとすぐ上限を超える。件数が増えると静かに壊れる
5. **重複蓄積は気づきにくい**: 「見た目は正常」でも裏側で30,847件になっていた。件数チェックを定期的に行う価値がある

## 2026-03-19: 月切替を触る UI テストは内部状態を直書きしない

### 状況
- GitHub Actions で `CSV出力` と `請求書CSV` の月切替系スモークテストが断続的に失敗した
- ローカルでは通る一方、CI では `currentMonth = new Date(...)` のような内部変数の直接変更が描画タイミングとずれて、3月のまま出力されることがあった
- 実運用の不具合ではなく、テストがブラウザ内部状態に寄りかかりすぎていたのが原因だった

### 教訓
1. **月切替の確認は必ず UI 操作で行え**: `→` ボタンや月表示テキストを経由して確認すれば、実際の利用手順と CI の挙動を揃えやすい
2. **内部変数の直接代入は最後の手段にしろ**: `currentMonth` のような状態は、描画・集計・ファイル名生成が完全に追従する保証が薄い
3. **ローカルで通るだけでは十分ではない**: GitHub Actions でだけ落ちるなら、速度の問題ではなくテストの前提が脆い可能性をまず疑う
4. **本体不具合とテスト不具合を切り分けろ**: 失敗通知が来ても、まず「本番機能が壊れた」のか「自動確認の書き方が揺れた」のかを分けて考える
